# @open-reloading/web

Next.js App Router (TypeScript, React). A static export: the browser reads data files and runs the simulations itself, and the build reads the API at `API_URL` (default `http://localhost:3000`) for the record pages. May import `@open-reloading/core` for computation in the browser. Package rules: root `AGENTS.md`.

## Records and lists

- `/cartridges`, `/cartridges/[id]`: server components reading the API through `apiGet` in `src/lib/api.ts` (`'use cache'`, `cacheLife('days')`).
  - `next build` reads the API (`tools/src/pages.ts` runs one over the data bundle) and prerenders every record page (the head tags and the loading state). A failed read fails the build.
  - Every record page (cartridge, bullet, powder, case, primer, target face, discipline, federation) is a small file: the server page (`src/app/<kind>/[id]/page.tsx`) holds the head tags (`recordMetadata` and `recordHeadText` in `src/lib/record-metadata.ts`: title, description, Open Graph and Twitter tags of the record) and a loading state under the record's name, and a client component (`<kind>-record-page.tsx` in `src/components/`) reads the record's data file in the browser and renders everything else: the figures (screen and print), the tables and the links. The shared parts: `RecordView` and `RecordViewWith` (`src/components/record-view.tsx`: loading state, failure with Retry, `PageNotFound` with `noindex` for a missing data file), `useRecord` and `useRead` (`src/components/use-record.ts`), `dataFile` (`src/lib/data-file.ts`). What a page reads besides its record (the manufacturer names, lists, the records its tables draw) goes through `apiFetch` (`readItems`, `readRecord` in `src/lib/record-reads.ts`), the fitting-bullet count of a cartridge too. What the API cannot answer, the server page computes at build and passes as a prop (the cartridges a bullet fits). Without JavaScript the page shows the name and a notice. A new record kind: the thin server page keeping `generateStaticParams` and `generateMetadata`, a client component on `RecordViewWith`, its entry in `recordHeadText` and in `lists` of `scripts/check-prerender.mts`, a row in `tests/web/record-page.spec.ts`.
  - The data files a page reads are not in its HTML: `dataFile` stores a file read before a service worker controlled the page in the records cache itself (`keepForOffline`), the worker stores the later ones, so a record opened once opens again offline.
  - `PRERENDER=sample` (root `AGENTS.md`) limits that to the records of `src/lib/prerender-sample.ts` (`sampleIds`, `pickIds`, read by `staticIds` in `src/lib/api.ts`). At least one id per route: the ids the e2e specs and the smoke set open. The export leaves every other cartridge page out, so a static host answers 404 for it (the data files stay complete, `exportIds`). An unknown id answers 404.
- Home (`src/app/page.tsx`): the page bar's h1 visually hidden (`titleHidden`), the top bar shows the whole wordmark there (`Brand` `full` in `site-header.tsx`; other pages cut it to its mark), the Tools and Library panels from `sections` as cards in one row each (stacked below 48em), the Library cards each with its tabs as links and the record counts of the Database tabs from the list routes at build time, then the What's new list (`home-news.tsx`, a server component): the newest five items of `apps/web/news/` (`YYYY-MM-DD-slug.md`, front matter `title` and `link`, two sentences), read at build by `newestNews` (`src/lib/news.ts`, the one file of `src` with a `node:` import), which fails the build on a malformed file. ## Static site

The web app is a static site without a server, for GitHub Pages or any static host: the records as data files and the simulations in the browser, with the docs site and the licenses beside it. `pages.yml` builds two editions into one deployment: the stable edition at the site root from the tag of the latest release, the next edition at `<root>/next/` from `main` (process: `apps/docs/docs/release.md`, Pages site). The e2e job of `ci.yml` builds its own export to test.

- `next.config.ts` is the only configuration: `output: 'export'` under `PAGES_BASE_PATH` (`''`, the site root, or a path such as `/Ballistics`) with `trailingSlash`, without Cache Components and Partial Prefetching (Next 16.4 exports only without them, `'use cache'` through `experimental.useCache`), no redirects.
  - `NEXT_PUBLIC_PAGES_BASE_PATH` is the base path in the browser (`src/lib/edition.ts`: `basePath`). A plain `<a href>` or asset URL to an app path takes `basePath`. `Link` and the router add it themselves.
  - `staticIds` prerenders every record (the sample of the static loop below cuts the cartridge pages only, `exportIds` in `src/lib/prerender-sample.ts`) and fails without the API.
- `apiFetch` is `src/lib/static-api.ts`, loaded on first use.
  - GET: lists from `catalogue/index.json` under `<base>/api/` opened with `openCatalogue` (`@open-reloading/api/catalogue`), the code the API's routes run, so paging, `q`, the filters (`table`, `manufacturer`, `cartridge` (powder tables, cases), `size` and `compound` (primers), `federation`, `discipline`, `face`), order and the refusals are the API's; a record from `<kind>/<id>.json`. Checked against the API by `test/static-api.test.ts`.
  - POST `interior` and `interior/charge-target`: validation, runs and answers of `@open-reloading/api/compute`, each compute task in a Web Worker of its own (`src/lib/compute.worker.ts`), terminated at the API's task deadline (503 `timeout`). A body above 64 KiB is refused (413): an interior body is under 1 KiB.
- `PAGES_EDITION` (`stable`, the default, or `next`; `tools/src/pages.ts` reads it, `next.config.ts` and `scripts/service-worker.mts` pass `next` on): the next edition's app base path is `<PAGES_BASE_PATH>/next` and its browser store has names of its own, because both editions share one origin.
  - `edition` and `storageName` in `src/lib/edition.ts` (`editionName` of `src/lib/offline.ts`) put `next:` ahead of every IndexedDB database name (`user-store.ts`), `localStorage` key (a new key is declared with `storageName`) and cache name. The stable edition keeps the plain names.
  - The service worker of each edition has its own scope (`<base>/`), shell caches and records cache. The stable worker's `strategyOf` leaves `<base>/next/` to the network.
- `PAGES_URL`: the site's origin (docs `url`, the web app's `metadataBase` and social image).
- Root `npm run pages:build` (`PAGES_BASE_PATH=<path> [PAGES_EDITION=next]` for a base path, `<path>` the site root's path; `tools/src/pages.ts`, after the root `npm run build`): starts the API over the catalogue of the data bundle (`@open-reloading/api/static`), builds the web app against it with `PRERENDER=full`, deletes each page's `__next._full.txt` (a copy of its `index.txt`, never requested by the export's client), writes the data files (`writeStaticApi`: the catalogue index and one file per record), builds the docs site into `docs/` (its code reference under `docs/library/`), copies LICENSE, NOTICE and `data/LICENSE` and writes `.nojekyll`. Output: `pages/` at the repository root (git-ignored). `.next` stays (CI's restored Turbopack cache, the manifests `check-weight` reads). `--no-docs` skips the docs site.
- Root `npm run pages:serve` (`tools/src/pages-serve.ts`): `pages/` under `PAGES_BASE_PATH` on `PORT` (default 3003). It does not read `PAGES_EDITION`: after a next build, `PAGES_BASE_PATH` is `<root>/next`, the app's base path, else the app's URLs answer 404. Directories answer with their `index.html`, a missing file the site's `404.html`.
- Static loop, the web app on data files without an API to start (`apps/e2e/AGENTS.md` for the checks), after the root `npm run build`:
  - `npm run dev:static` at the root (`tools/src/static-dev.ts`): writes the data files (`writeStaticApi`) into `apps/web/public/api/` (git-ignored, removed when the run ends and by `pages:build`), starts `next dev` at the site root on port 3000 (`PORT` for another). The data files are what the browser reads; the server side of a record page reads the API over the catalogue of the data bundle, which this process runs in-process for the length of the run. Ctrl+C ends both. `next dev` logs React warnings (duplicate keys in source lists, image sizes) that the production build does not.
  - `npm run static:build` at the root (`pages:build` with `--sample`): the export at the site root in `pages/`, `PRERENDER=sample` (the inherited value is never used, `pages:build` without `--sample` always builds every record), no docs site, about 85 MB in about 15 s. The data files are complete. Of the record pages the sample cuts the cartridge pages only (`exportIds`: an exported page outside the sample answers 404 and the links to it log that, so a spec that navigates between records starts where every linked cartridge is in the sample); the cartridges the specs open are in `src/lib/prerender-sample.ts`. `npm run pages:serve` then serves it at `http://localhost:3003/`.
- Offline: the service worker precaches `api/catalogue/index.json` with the static files (`precacheList`, `catalogueFile` in `src/lib/offline.ts`) and answers it from the shell cache; record files stay network-first.
- E2E: project `full` against the export at the site root, project `pages` with `PAGES_URL` for the base path (`apps/e2e/AGENTS.md`).
- Size: about 300 MB per edition, the cartridge pages about 265 MB of it, so the deployed site (both editions) is about 600 MB. The 1 GB limit of `apps/docs/docs/ci-tools.md` applies to the deployed site.

  - A button for two units, a menu for three or more. Nothing is stored. The Settings (`UnitsForm`) store units. A change of the Settings or a reload resets the field.
  - A numeric `placeholder` and a message, mark or help that names a unit (`error`, `mark`, `help`, `action.text`, `fieldError(spec, value, shown)`) are functions of the units shown. `unit="text"` or `"none"` leaves a page without switches.

## Language

The language is a setting: one page tree, one set of URLs, no locale in paths. English is the source text in the code. Every other language is one catalogue file, loaded in the browser when it is chosen. Contributor steps: `apps/docs/docs/translating.md`.

- Settings, General, Language (English, Deutsch; `LanguageChoice` in `settings-sections.tsx`) stores the code in `localStorage` (`language`, `storageName`).
  - `src/i18n/language.ts`: `languages`, `loaders` (one dynamic import per language but English, so English pages ship without a catalogue), `chooseLanguage`, `startLanguage` (called in `Providers` after mounting) and `useTranslation()`. The server render and hydration are English, then the stored language applies (the units' pattern: no stored value is known while hydrating). A page shows English first for a German user.
  - `<html lang>` follows the language shown: it changes when the catalogue has loaded, so a page never says German over English text. A load that fails (offline, never opened in that language) keeps English and the choice.
- Terms: user-facing text says target and targets (the Targets list, the Target designer), never target face or face; Brass names the Cases list, a record of it and the user's group (Brass group, My brass), case a physical case, a part or a measurement (case capacity, case length, trim length, neck wall). Code identifiers, routes, schema fields and stored keys keep their names. A name from a rule book or a product keeps its spelling.
- `src/i18n/translate.ts` (pure): `t('English text', { name })`, `tn(count, '{count} record', '{count} records')` and `msg('English text')` for data that `t` translates where it is shown (`sections.ts`, `your-data.ts`). The catalogue key is the English text, a plural's key is `one|other`. A text the catalogue lacks is shown as written. A key may start with a context and U+0004 (`'material\u0004Brass'`, `'charge\u0004Target'`) where one English word has two senses; English shows the text after it. `{name}` placeholders, a number value formatted with the language shown (decimal separator, no grouping). The types accept a string literal or a `Message`: a text built at run time does not compile, so none escapes extraction.
  - Text in JSX goes through `t` in an expression: `{t('Close')}`. A plain attribute or child string is not extracted.
  - A model, record name, exported file field name and the text inside the packages are not translated.
  - A function in `src/lib` that writes text takes the translator as its last parameter (`t`, `tn`) and `untranslated()` / `english.t` (`translate.ts`) stands for English where a file or a link writes it. A field spec's label and help are `msg` values translated with `specText(t, text)` (`field-spec.ts`); `fieldError(spec, value, shown, t)` writes the error.
  - State that outlives a language change (the workbench status, the charge-target answer) keeps a `Say` (`translate.ts`: a function of the translator) or the English text for `translateMessage`, never the translated string, and writes it where it is shown. A ladder reason (`stepError`, the ladder plan's `error`) is still stored as written.
  - A message that came from the packages, the API or the app's own request code (a refusal, a reason code, a warning) stays English in state, links and files and is translated where it is shown with `translateMessage(text, t)` (`src/lib/core-messages.ts`). Its table is `src/lib/core-message-table.json` (read by `scripts/i18n.mts` like the `msg` calls, a JSON file because a long run of `msg` lines counts as duplicated code for the SonarCloud gate) with the warning codes in `core-message-table.ts`: the reason codes and warning codes of core and the API, and the sentence templates of `InputError`, which has no codes. The language module loads the table with a catalogue other than English, so English pages ship without it. `test/core-messages.test.ts` scans `packages/core/src` and `packages/api/src` and fails for a message the table lacks, so a new refusal needs its German text in the same change.
- `src/i18n/<code>.json`: key to text, or to `{ one, other }` (the CLDR plural categories of the language). `npm run i18n -w @open-reloading/web -- missing <code>` lists the English messages the catalogue lacks and exits 1 for a key no message matches; `-- messages` lists every message (`scripts/i18n.mts`, a text scan of the files that import from `src/i18n/`, `translate.ts` included).
- `test/i18n-catalogue.test.ts`: no catalogue key without a message in the sources, the placeholders of a text equal those of its key, and the German catalogue writes a verified term of the table as the table does where its English word occurs (the words of a multi-word row pair up by position) and a rejected candidate of a decided row nowhere its English word occurs. A longer term of the table owns its words ("Target face" is not "Target"). A text that uses the English word in another sense, or that the table's own term replaces, is listed in `otherSense` with the sense. `test/i18n.test.ts`: the fallback, plurals, numbers, the stored choice and the document language.
- Numbers, dates and countries follow the language shown, with no catalogue entry: `src/i18n/number.ts` is the one formatter and the one parser, `src/i18n/shown.ts` holds the language that `publish()` of `language.ts` sets.
  - Canonical text (point decimal, what `Number()` reads) is what the app holds everywhere: field state, URLs, share links, user data, saved loads, CSV, JSON and downloaded files, the clipboard copy of a table (`canonicalNumberText`), the API. Only the screen writes the language's decimal mark (`formatNumber`, `fixedNumber`, `plainNumber`, `localizeNumber` for canonical text, `localizeDecimals` and `<Decimal>` or `FieldRow.numeric` for numbers in server-built text) and only text a person types or pastes is read through `parseNumber`. Never `toFixed`, `String(n)` or a template number in display text. An export passes `'en'` to `formatNumber`.
  - `parseNumber(input, { min, max, integer }, language)` returns `empty`, `number` (value and canonical text), `invalid` or `ambiguous`. The rule is in `apps/docs/docs/translating.md`. `NumberField` under a decimal comma is a text input read by `parseNumber` (`typedFieldValue` in `field-spec.ts`), under a point a signed field stays a native number input and an unsigned one a Mantine `NumberInput` whose pasted text goes through `parseNumber`. The theme's `NumberInput` `decimalSeparator` follows the language (`themeFor`).
  - Dates: `dayText`, `dateTimeText`, `timeText` (`lib/dates.ts`) use `Intl` for the language, English keeps its form. Country names: `countryName` (`lib/countries.ts`), English keeps the record's name. Caliber designations (`.308`, `7.82 mm`), stored photo notes and the text inside the packages stay canonical.
  - `test/number-format.test.ts` (formatter, parser, round trips), `test/number-field.test.tsx`, `test/language-exports.test.ts` (exports are the same under both languages), `tests/web/german-numbers.spec.ts`.
- Offline: the catalogue is a chunk under `.next/static`, so the worker precaches it with the other chunks (`precacheList`) and answers it from the shell cache. `tests/web/language.spec.ts` reopens the German home page offline and runs axe on the German workbench after the example run.
- Translated so far: the home page, Settings (the dialog, General, `UnitsForm`, the Workbench tab and its field labels and errors, the Manufacturers section), the Database (the list pages of every kind, the record pages of cartridge, bullet, powder, case, primer, target face, discipline and federation, the bullet comparison and the burn-rate comparison) and the workbench: inputs, results, charts, tabs, notes, ladders, seating, trajectory, measurements and the messages of the packages and the API (`translateMessage`), the File menu and saved loads, the chronograph file import, the session summary, Shot groups (with the hole detection and ring scoring), range mode, the firearm library and the editors of the user's own firearms, cases and lots, Settings (Your data, Keyboard, Offline), the designers (cartridge, bullet with the photo tool, powder, target face, their print-only text too), the navigation (top bar, sidebar, drawer), the site search, the shortcuts help, the report dialog, the error, not-found and offline pages. Still English in the Database: the `metadata` of every page (the head tags the export holds are one language), record names, notes and source fields as published, and the text of the drawing figures from `@open-reloading/drawing`. Printed pages follow the language shown: the workbench report, the load sheets, the range card, the target sheet and the ladder target (their long German words break inside the cell, `overflow-wrap` in the print rules of `globals.css`). Printed pages carry the date as `YYYY-MM-DD` in both languages. The tab Trajectory keeps some label ellipses at 1280 px in German (the full text is in the field's name).
- Data a lib builder or a server page hands to a client component carries its text as `Wording` (`src/lib/wording.ts`): a `msg` message, `verbatim(name)` for a name or printed value, or `worded(message, values)`; the client shows it with `say(t, wording)`. `FieldRow.label`, `FieldRow.method`, `FieldGroup.title` and `FieldGroup.filter` are `Wording`, the stored enumerated values of the records go through `src/lib/record-values.ts` (a value the map lacks shows as the record gives it).
- `PageBar` and `Panel` show a record's name or a ready text as it is, and with `translated` a `Message` (`listTitles`). `Loading`, `ListLoading`, `DataError` and `EmptyList` take a key of a table of whole sentences in `states.tsx` (`loadingLines`, `unavailableLines`, `noMatchLines`): a new place that loads or lists gets its sentence there.

## German terms

- `src/i18n/german-terms.json`: the term table of the German interface, one row per term with its key, English term, group, status (`verified`, `decided`, `unverified`), the German word, and its sources as a document id and a place (section or page), never a passage. The document ids and their editions are the file's `sources`.
  - Verified: one German word and at least one source. Decided: at least two candidates, each with its own source, `german` one of them and `decision` the rule that chose it (the rule order is in `apps/docs/docs/translating.md`). Unverified: a candidate or null, and a note that starts "Accepted as candidate for 1.0" followed by what was searched. A candidate is never a source.
  - Rows are edited by hand. `test/german-terms.test.ts` checks the format.

## Streamed pages

- A page that waits for its data inside a Suspense boundary (the list pages, `src/app/cartridges/page.tsx`) streams. React 19.3 reveals a streamed boundary up to about 300 ms after the first paint.
- A provider above the page whose context value changes after mounting makes React client-render the waiting boundary. A hidden `div#S:n` copy of the page stays until the reveal.
- Providers above `main` keep one context value for the page's life. `useUnits` reads a store behind a constant context. The page sits in `AppShell.Main`: AppShell keeps its context value stable (`@mantine/core` 9.7.4 and later), so the streamed page is not client-rendered twice.

## Commands (this directory, or `-w @open-reloading/web` from the root)

- Dev server: `npm run dev:static` at the root (it writes the data files the browser reads and runs the API the server side needs, see the static loop below)
- Build: the export, `npm run static:build` or `npm run pages:build` at the root (`npm run build` here is the export build they run, which needs the API at `API_URL`)
- Type check: `npm run typecheck` (generates route types first)
- Test: `npm test` (Vitest, `test/`)
- Coverage: `npm run test:coverage` (v8 over `src`, no threshold, report in `coverage/lcov.info`). The excluded files and their reasons are in `vitest.config.ts`.
- Prerender check after an export: `node scripts/check-prerender.mts` (reads `pages/` at the repository root), with the `PRERENDER` value of the export (`sample` for `--sample`). It lists the ids from the export's data files (`api/<kind>/*.json`) and fails for a list or record route without `index.html` or `index.txt`: every record, or with `sample` the sample cartridges and every record of the other kinds. A record page whose HTML lacks one of the six head values of its record (its data file and the manufacturer files through `recordHeadText`; an empty tag or another record's tags fail) fails too (`checkPages`, `test/check-prerender.test.ts`).
- Build workers: `next.config.ts` caps the static generation workers at 8 (`experimental.cpus`, `BUILD_WORKERS` for another number). The default is one per hardware thread but one.
- JavaScript budget: `npm run check-weight` after an export build (`npm run static:build`, which leaves `.next`; CI: the `e2e` job, after the export). Per route of `.next/app-path-routes-manifest.json` it sums the gzip level 9 bytes of each JavaScript file once, as `initial` (root main and polyfill files, the client chunks of the page and its layouts) and `total` (`initial` plus the lazy chunks of the page's `react-loadable-manifest.json`), and fails when a route is over the `budget` of its group in `weight-budget.json`, or is in no group, or a group lists a route the build lacks. The `routes` values in the file are the recorded weights the job summary's change column compares with. The table also shows each route's headroom (budget minus the measured value), and a route with less than 1 % of its budget left (half the 2 % margin of the rule below) gets a warning line, which does not fail the check. The export is measured: its client holds the data file reader and the compute worker's loader. Core and importers are marked `"sideEffects": false`, so a page takes only the modules of their index its imports reach, not every module the index re-exports: code that only a worker or a lazily loaded page uses stays in their chunks. The number does not depend on the API, `PRERENDER` or the build directory, but on the Node's zlib: record the values in the dev container (CI's `.nvmrc` Node), not with a host Node. When a budget is set or raised, it is the largest recorded value of its group plus 2 %, rounded up to 1000 B (recorded values may later grow into that margin, the test keeps a budget at least at the largest recorded value): raise it only in a pull request that says why. Record the values whenever a budget is set or raised. A new route goes into a group, or a new group.
- What a CI run or a local run must build, from the changed files: `node scripts/ci-plan.mts`. It prints `check=`, `e2e=` (the API's conformance run and the e2e tests on the export) and `prerender=`. The export scripts of `tools/src` are inputs of `e2e`. Rules in the script, test `test/ci-plan.test.ts`.
  - CI: `EVENT_NAME`, `BASE_SHA`. Local: `--stamp apps/web/.next/ci-plan-stamp`, `--require full`.
  - After a build on a clean tree: `--write-stamp apps/web/.next/ci-plan-stamp --prerender <mode>`.
- Build cache: `.next/cache/turbopack` is reusable between builds. `.next/cache/fetch-cache` holds API responses (`cacheLife('days')`: a warm build would serve old record data), so `prebuild` deletes it and CI never caches it.
